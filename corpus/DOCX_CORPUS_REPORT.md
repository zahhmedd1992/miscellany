# DOCX_CORPUS_REPORT — what was gathered, what was proved, and what a reader author needs to know

**Locked 2026-08-22.** 40 files, 11.7 MB, SHA-256 locked in `corpus/docx.json`, published in
`CORPUS_DOCX.md`. Tier A 20 representative, Tier B 20 adversarial. All six sanity gates pass.
Zero candidates were rejected for being inconvenient; the three that were rejected are listed
with their leading bytes.

The last section is the one worth reading. Everything before it is provenance.

template, a fillable MOU, a policy, four university thesis templates, three WHO report

### Tier B — 20 adversarial: 18 downloaded, 2 derived

Eight distinct `<Application>` strings, one strict-conformance file, three files whose
namespace prefix is not `w`, and a scale range from 3 zip parts to 910.

**`origin: derived`** means built by deterministic code in `build_docx_corpus.py` from a source
that is itself URL- and hash-locked, so a fresh clone reproduces the exact bytes. Nothing in
this corpus was produced by running a local Word or LibreOffice: both stamp timestamps, rsids
and GUIDs into every save, so a locally-generated file could never be re-verified against a
hash. Word was used only to *validate* the derived files (§5).

## 2. How it was sourced — so the negative claims are auditable

Two methods failed and are recorded because the failure is informative:

**Guessing filenames: 2 hits from 32.** Plausible paths on `nih.gov`, `nsf.gov`, `fema.gov`,
`gsa.gov`, `epa.gov`, `energy.gov`, `nasa.gov`, `hhs.gov`, `nist.gov`, `usda.gov`, `mdpi.com`,
`plos.org`, `frontiersin.org`, `springernature.com` and `ec.europa.eu` were nearly all 404.

**Scraping landing pages: 2 hits from 15.** `/forms`, `/templates-forms`, `/authors/layout`
are client-rendered shells. `gsa.gov/forms` returned 1 MB of HTML containing zero `.docx`
links — a rendered index, not an empty one.

Three methods worked:

**`filetype:docx site:gov` / `site:edu` search** — the highest-yield channel by far. Genre
sweeps (meeting minutes, annual report, policy, thesis template, report template) returned
live URLs directly; **34 of 36 probed returned real PK-zip `.docx`.**

**Directory-index walking.** `ftp.3gpp.org` serves an open autoindex. Note the trap:
`www.3gpp.org/ftp/…` returns **403** while `ftp.3gpp.org/…` serves the identical tree at 200,
and the autoindex's own links point at the 403 host. Rewriting the host is what turned that
source from "blocked" into three real standards documents.

**GitHub contents API over OSS test suites.** Enumerating beats guessing: `apache/poi`
test-data (130 `.docx`), `apache/tika` test-documents (56), `aspose-words` Examples/Data (237),
`jgm/pandoc` test/docx (85) + golden (38), `mammoth.js` (17), `python-mammoth` (17),
`python-docx` (4), `python-docx-template` (40), `docxtemplater` examples (168),
`docx2python` resources (41). 107 were downloaded to a staging pool and characterised, and
Tier B was then selected **on measured evidence rather than on filename**.

That last distinction earned its keep twice. `docxtpl-comments.docx` contains **zero comments**.
The `Aspose.Words` Examples/Data folder is mostly *Word-authored inputs*, not Aspose output —
labelling those files "generated by Aspose" would have been a fabricated provenance claim.

### G2 deserves its own paragraph, because as written it was wrong

The gate says a zero is *"either a broken download or a broken characteriser — find out which."*
Two files return zero. **They are neither.** There is a third case:

- **`adv-header-footer-only`** — the body is one empty `<w:p/>` plus a `sectPr` referencing six
  header/footer parts. All 54 characters live in `word/header2.xml` and `word/footer2.xml`.
- **`adv-wps-office`** — WPS Office wrote a document whose runs hold `<w:object>` elements
  wrapping OLE embeddings: 9 objects across 10 embedding parts, and no `<w:t>` anywhere in the
  package.

**Both therefore share a `textSha256`** — `e3b0c44298fc1c14…`, the SHA-256 of the empty
string. That is correct and unavoidable: two documents with no text have the same text. Gate G3
checks *file* sha256, which are distinct, so nothing here is wrong. But a reader test that adds
"every `textSha256` is unique" as a cheap sanity check will fail on exactly these two files, and
whoever writes it will lose an hour. It is not a duplicate; it is an empty document.

Both were confirmed by a **second, independent implementation** — a raw regex over the XML bytes,
agreeing with the ElementTree count at 0. So the resolution was not to delete the files or fudge
the number, but to make the gate *narrower*: each zero must carry a recorded reason **and a
predicate that is re-evaluated on every run**. If a download silently becomes a 404 page, the
predicate stops holding and G2 fails again. An exemption that cannot go stale is the only kind
worth granting. Both reasons are published in `docx.json` as `zeroTextReason`.

## 6. What a reader author should know before writing one

This is the section the corpus exists to produce. Every item below is a measured fact about
these 40 files, not a reading of the spec.

### 6.1 The prefix trap is *inverted* from the xlsx side

In SpreadsheetML the ordinary case is a default namespace (`<worksheet><c>`) and a prefix
(`<x:c>`) is the surprise — 12 of 49 files, and it made the first xlsx characteriser call four
files empty.

**WordprocessingML is the other way round.** 37 of 40 files use `w:`, and *every one of the 20
real-world Tier A files does*. The consequence is worse, not better: a reader can hardcode the
literal string `"w:"`, pass a corpus of real documents 100%, and be silently broken. Nothing in
normal usage will ever catch it.

`adv-prefix-ns0` proves a non-`w` prefix occurs naturally — it is pandoc's own test fixture, not
something invented for this corpus. `adv-prefix-default` and `adv-prefix-exotic` cover `∅` and
`zzz`. All three parse to `31` paragraphs, `29` runs, `253` chars and
`textSha256 66c66de03f105891` — **identical to the `w:`-prefixed source**. If a reader produces
three different answers for those three files, it is matching on prefixes.

### 6.2 There are two OOXML namespaces, not one

| Class | Namespace |
|---|---|
| Transitional (39 files) | `http://schemas.openxmlformats.org/wordprocessingml/2006/main` |
| **Strict** (1 file) | `http://purl.oclc.org/ooxml/wordprocessingml/main` |

Word writes transitional by default and strict when asked ("Strict Open XML Document" in the
Save-As dialog). A reader that hardcodes the transitional URI opens `adv-strict-ooxml`, finds
zero paragraphs, and reports success. Every drawing, math and relationship namespace has a
matching `purl.oclc.org` twin.

### 6.3 Match on local name **and** namespace, never on either alone

Matching by namespace only is 6.2's bug. Matching by local name only is its mirror: `<m:r>` is an
OMML math run, `<w:r>` is a text run, and they mean different things.

| File | `w:r` | `m:r` | A local-name scan reports |
|---|---:|---:|---:|
| `acm-taps-template` | 2,148 | 19 | 2,167 |
| `gatech-thesis` | 793 | 10 | 803 |

Off by 0.9% — small enough to look like a rounding difference, large enough to be a bug.

### 6.4 `word/document.xml` is a convention, not a rule

`adv-alt-doc-path` keeps its main part at **`word/document2.xml`**. The correct resolution is
OPC: read `_rels/.rels`, find the relationship whose `Type` ends in `/officeDocument`, follow its
`Target`. A path check passes on 39 of 40 files, which is exactly the hit rate that gets a
shortcut shipped.

### 6.5 Recursion over the element tree has a real cliff

`adv-deep-tables` nests tables **4,999 deep**, giving a maximum element depth of **15,004**.

This is not hypothetical: the first version of the nested-table counter in
`build_docx_corpus.py` was a four-line recursive walk and died with `RecursionError` before
counting anything. It was rewritten with an explicit stack. Any reader that recurses over
paragraphs, tables or runs has the same cliff, and a 15,000-deep document is a *valid* document.

### 6.6 `<w:t>` is not "the text"

Four separate ways text hides from a `<w:t>` scan, all present in this corpus:

1. **Headers and footers** are separate parts. `adv-header-footer-only` has **0** characters in
   `document.xml` and 54 in `header2.xml`/`footer2.xml`.
2. **`<w:delText>`** holds tracked-deleted text. 192 characters across two files. A `<w:t>` scan
   never sees it — which is usually correct, but it is a decision, not a default.
3. **Footnotes, endnotes and comments** live in their own parts.
4. **`<w:instrText>`** holds field instructions, which look like text and are not.

### 6.7 `mc:AlternateContent` duplicates text on purpose

19 occurrences in `adv-all-features` alone, 46 across the corpus. A `Choice` and a `Fallback`
describe the *same* content two ways — a modern DrawingML shape and a legacy VML one — and both
carry `<w:t>`.

A flat scan counts that text **twice**; a reader honouring markup compatibility counts it once.
Neither is wrong, but they will never agree, so the reader test must be told which convention
the lock uses. **`textChars` here is the flat count**, because it is the one a byte-level scanner
reproduces without first implementing MCE resolution.

### 6.8 `xml:space="preserve"` is not decoration

**13,261** `<w:t>` elements across the corpus carry it. A reader that trims or collapses
whitespace destroys real content, and the damage is invisible in a rendered view because the
surrounding text still reads correctly. There are also **43** empty `<w:t/>` elements; skipping
them versus contributing `""` changes nothing about `textChars` and nothing about `textSha256` —
but only because the definition was fixed before the numbers were taken.

### 6.9 The `<Application>` string is a claim, not an observation

| What it says | What it is |
|---|---|
| `Microsoft Word 12.0.0` (3 files) | **pandoc** — it copies its reference document's metadata |
| `unknown` (4 files) | Google Docs and Apple Pages ship **no `docProps/app.xml` at all** |
| `Microsoft Office Word` vs `Microsoft word` | two different producers, differing only in case |

Never branch reader behaviour on the generator string.

### 6.10 A footnote count of 2 usually means zero footnotes

`word/footnotes.xml` always contains two built-in entries — the separator and the continuation
separator — with ids `-1` and `0`. **17 of 40 files** carry exactly two `<w:footnote>` elements and
**zero** actual `<w:footnoteReference>`; **23** have a `<w:footnote>` count that exceeds their real
reference count by exactly those two.

A reader that reports `footnotes.xml`'s element count tells the user every document has two
footnotes. Count `<w:footnoteReference>` in the body for the number a human means. Both are in the
lock (`footnotes` and `footnoteRefs`) precisely so the difference cannot be papered over.

### 6.11 `<w:sectPr>` count ≠ number of distinct page layouts

`baylor-dissertation` has **7** `sectPr` and **1** distinct page setup. `adv-page-setups` has 7
and **3**, one of them landscape. Also: the final `sectPr` is a direct child of `<w:body>` while
the others hang off `<w:pPr>`, and `<w:sectPrChange>` nests *another* `sectPr` inside a tracked
change. Counting `sectPr` occurrences answers a different question than "how many page layouts".

### 6.12 A paragraph can be numbered without a `<w:numPr>`

`numberedParas` counts `<w:p>` whose **own** `<w:pPr>` holds a `<w:numPr>`. Two ways that
undercounts: numbering inherited from a paragraph *style*, and `<w:numPr>` overridden at the
style level. Conversely, searching a paragraph's whole subtree over-counts, because a paragraph
in a nested table inside it would mark the outer paragraph numbered. The subtree version is the
easy bug, and the 3 files with nested tables are where it fires.

### 6.13 A password-protected `.docx` is not a zip

Leading bytes `D0 CF 11 E0` — an OLE/CFB compound file with the OOXML package encrypted inside.
`zipfile` raises `BadZipFile`, which reads exactly like a corrupt download and sends someone
hunting a bug that does not exist. Branch on the magic and say *encrypted*. A truncated zip
starts with `PK` and fails differently; conflating the two costs an afternoon.

### 6.14 Word's own numbers will not match yours, and both are right

Word reports **40 paragraphs / 325 characters** for `adv-pandoc-tables`; the XML holds **31**
`<w:p>` and **253** characters of `<w:t>`. Word's object model inserts an end-of-cell mark per
cell and an end-of-row mark per row. Anyone validating a reader against Word's UI counts will
chase a discrepancy that is not a defect. Recorded in `docx.json → wordValidation`.

### 6.15 Scale and features fail differently

`adv-many-paragraphs` is 31,190 paragraphs, 50,128 runs, 800,115 characters, 661 tables,
25,241 cells and 6,657 merge marks — and **910 zip entries**, because 164 of them are images.
At the other end, `adv-deep-tables` is **3 parts** and has no `styles.xml` at all, while
`adv-libreoffice-lin` is 2.9 MB across 30 parts from just 5 paragraphs.

Those are three unrelated scaling axes — body size, part count, tree depth — and a reader can be
fine on two and fall over on the third. The xlsx side learned this the expensive way: every test
opened small workbooks, and the failure only appeared on the first *edit* of a large one.

### 6.16 A free tracked-changes oracle

`3gpp-working-proc` and `3gpp-working-proc-rm` are the clean and revision-marked issues of the
same real standards document:

|  | clean | revision-marked |
|---|---:|---:|
| body paragraphs | 804 | 804 |
| all paragraphs | 1,156 | 1,156 |
| runs | 3,155 | **3,166** |
| textChars | 85,139 | 85,139 |
| **textSha256** | `da256ea483719e46…` | **`da256ea483719e46…`** |
| insertions / deletions | 0 / 0 | 23 / 5 |
| `w:delText` chars | 0 | 104 |

**Identical text hash, different files.** The revision marks split 11 extra runs and move 104
characters into `<w:delText>`, but the accepted text is byte-identical. A reader that resolves
tracked changes correctly must produce the same `textSha256` for both; one that leaks deleted
text into the body will not. That equivalence was not designed — it was found by measuring, and
it is the single most useful assertion pair in the corpus.

## 7. Reproducing this

```bash
python corpus/build_docx_corpus.py                   # verify on-disk hashes against the lock
python corpus/build_docx_corpus.py --gates           # the six sanity gates
python corpus/build_docx_corpus.py --refetch         # re-download every URL, compare sha256
python corpus/build_docx_corpus.py --recharacterise  # re-measure from disk, hashes ASSERTED
python corpus/build_docx_corpus.py --rebuild         # full rebuild from scratch
python corpus/build_docx_corpus.py --publish         # regenerate ../CORPUS_DOCX.md from the lock
```

`--recharacterise` asserts every sha256 is unchanged *before* recomputing, so a characteriser fix
can never silently move the goalposts by quietly pulling a newer upstream file underneath the
numbers. That mode exists because the xlsx corpus needed it — the first characteriser there was
wrong, and re-downloading to fix it would have changed the exam.

### What a `MOVED` result from `--refetch` means, and the one real fragility

All 40 verified identical on 2026-08-22. They will not stay that way. **20 of the Tier A files
come from live `.gov` / `.edu` / `who.int` URLs that get republished without notice**, and a
`MOVED` line does **not** mean the corpus is broken — it means upstream changed and the bytes on
disk are now the only copy of what was graded.

Because `corpus/docx/files/` is gitignored, that has a consequence worth stating plainly:
**once any of those URLs rot, a fresh clone can no longer rebuild the full Tier A.** The lock
still records exactly what was measured, and the reader test still asserts against it, but the
files themselves would need to come from a machine that already has them. If this corpus is ever
going to outlive its sources, the fix is to archive the 11.7 MB somewhere durable — not to
re-fetch and re-lock, which would silently change the exam.

`--verify-docs` deserves one caveat too. Its `PROSE_CLAIMS` table hardcodes the expected value of
each number quoted in this report. That catches a lock/document mismatch, but the constant and
the sentence are two copies of one fact: **if you change a `PROSE_CLAIMS` value, change the
sentence it mirrors as well**, or the checker will pass while the prose is wrong.
