02 — THE ONE IDEA

Why this is buildable, and why nobody has it

Every office suite ever built is separate programs that exchange files. Word, Excel and PowerPoint are three codebases; "paste a chart into a slide" is a fragile bridge between them, which is why linked charts in PowerPoint have been notoriously broken for twenty years.

What you described is different. You want one thing that can wear different faces. That has a precise technical shape:

A spreadsheet already contains the whole architecture

Think about what a spreadsheet actually is under the hood. It's not a grid. It's a dependency graph: C1 depends on B4:B16, so when B7 changes, something marks C1 dirty and recalculates it. That graph plus a recalculation scheduler is the spreadsheet. The grid is just a way of looking at it.

Now: a chart on a slide that updates when a cell changes is the same problem. A form field bound to a data source is the same problem. A document paragraph showing a live total is the same problem.

Build the dependency graph once, and every "integration" between apps you'd otherwise have to write is already done — because it was never two apps.

So Grain is four pieces, and the first one is the load-bearing one:

PieceWhat it isWhat it buys
Node graphEvery cell, shape, paragraph, field is a node with a value, an optional formula, a style, and dependents. One recalculation scheduler.Apps compose for free. A chart on a slide is just a node that depends on a range.
Command registryEvery action the software can take is declared once — id, arguments, what it touches.Keyboard shortcut, menu item, script call, HTTP endpoint and AI tool all generate from one declaration.
Capability manifestEvery module declares what it needs: files, network, clipboard. Nothing gets ambient access."Secure" becomes an enforceable property, and a plain-English permission list for the user.
View shellThe UI is generated from the command registry filtered by a profile.Your ribbon complaint, solved as configuration, not as a fork.

Two worked examples make this concrete. They're the part worth reading closely — the rest of this document is scaffolding around them.

03 — WORKED EXAMPLE ONE

Excel + PowerPoint, actually merged

Your test case. Here is literally what happens.

You have a model in Sheet and a board deck in Deck. You want the revenue chart on slide 3 to be the real numbers, always.

// Both documents live in the same node graph.
// The chart is not a copy. It is a node that depends on a range.

sheet:q3-model/B4:B16   → 13 value nodes
deck:board/s3/chart-1   → node { source: ref("sheet:q3-model/B4:B16") }

Now edit B7. Here is the entire mechanism:

1. B7 changes
2. Scheduler walks dependents of B7  — the same walk that updates =SUM(B4:B16)
3. chart-1 is in that list          — it's an ordinary dependent, nothing special
4. chart-1 marked dirty → slide 3 repaints

There is no link, no paste-special, no sync job, no file boundary, no integration code. Step 2 is machinery a spreadsheet needs anyway. The chart got live updates for free, because it was never a different program.

Why this beats Office rather than just matching it

In PowerPoint, a linked Excel chart is bound to a file path. Move the file, rename the folder, email the deck — the link breaks. Everyone has seen this.

Here the reference is a stable node id inside one document. There is no path to break. And when you export to .xlsx + .pptx for someone on Office, re-importing the pair rebuilds the connection — because the id survives the round trip.

What "combine the two into one dual solution" means in practice

Open a deck. Press Ctrl+K, type "sheet". You now have a grid pane and a slide pane over one document. Sheet and Deck were never separate downloads with an integration — they are two view profiles over the same graph. Using one alone is the default; using both is one keystroke.

04 — WORKED EXAMPLE TWO

The 400-button problem

Your ribbon observation, turned into a mechanism.

You said it exactly right: Excel's header is hundreds of buttons of which almost nobody uses more than a handful. The usual response is "we made a simpler app" — which means a fork, a second codebase, and a ceiling the user hits and can't pass.

Because every action is declared in one registry, the toolbar is not code. It's a list:

// profiles/sheet.simple.json — the entire "simple mode"
{
  "extends": "sheet.default",
  "toolbar": [
    "fmt.bold", "fmt.number.currency", "fmt.number.percent",
    "edit.undo", "edit.redo",
    "data.sort", "data.filter",
    "insert.chart", "view.freeze", "file.save"
  ],
  "hide": ["*"]   // everything else: palette-only, not deleted
}

Ten buttons. And here is the part that makes minimalism safe rather than limiting:

The other 390 commands aren't removed. They're one Ctrl+K away, searchable by name.

A beginner sees ten buttons and is never lost. A power user types "conditional format" and gets it instantly — faster than finding it in a ribbon. Nobody hits a ceiling, and there is no second codebase. This is the lesson VS Code proved at enormous scale, applied to the place it's needed most.

The same file drives a stripped-down build for a school, a finance-specific profile with modeling commands surfaced, or a kiosk with three buttons. Configuration, not forks. That's what "modular" has to mean to be worth anything.

05 — CONNECTING TO THE OUTSIDE WORLD

The API you don't have to write

You described this one without the vocabulary. Here's the vocabulary, and why it's nearly free.

Normally, giving software an API means building a second product: design endpoints, write handlers, keep them in sync with the app, document them, watch them rot.

Not here. Every action is already a declared command with typed arguments. So the API is a projection of the registry:

// declared once, by the feature author
command("data.sort", {
  args:  { range: "Range", by: "Column", dir: "asc|desc" },
  needs: ["doc.write"],
  describe: "Sort a range by a column."
})

// and it automatically exists as all of these:
keyboard   Ctrl+Shift+S
menu       Data → Sort
palette    Ctrl+K "sort"
script     ms.data.sort({range:"A1:D50", by:"C", dir:"desc"})
http       POST /v1/cmd/data.sort
AI tool    exposed over MCP — any assistant can call it

MCP (Model Context Protocol) is the open standard for letting an AI assistant use a tool. Because our commands already carry names, typed arguments and descriptions, the MCP server is a generated adapter — not a hand-written integration.

What that buys, concretely: someone points Claude or ChatGPT at their Miscellany and says "take this CSV, build the Q3 model, and make me a board deck from it." The assistant calls the same commands a human's keystrokes call. No plugin, no scripting language to learn, no vendor to ask permission from.

And the reverse direction

AI inside the apps goes through one capability-gated bridge — bring your own key, or point it at a local model on your own machine. No Miscellany account, no Miscellany server, no per-seat AI tax. If you use a local model, your data never leaves the building. That is the ownership pillar applied to the thing everyone else is currently using to create new lock-in.

06 — SECURITY

What "secure" is allowed to mean, and when

This word is usually decoration. Here is exactly what it buys at each stage, including where it buys nothing yet.

StageEnforcement mechanismHonest strength
1–2
first-party only		 Capability manifests declared per module; a CI check fails the build if code touches something it didn't declare. Advisory. This is a discipline and an audit trail, not a sandbox. Safe only because every line is first-party.
3
real isolation		 Modules run in a separate context — Web Worker in browser, isolated process on desktop. No DOM, no filesystem, no network handles. Every privileged call crosses an IPC boundary to a broker written in Rust that checks the granted set. Enforced. A module can't read a file it wasn't granted because it holds no function that can.
4
third parties		 Above, plus WASM Component Model for compute-heavy modules — capability-based by construction — plus signed modules and a published review bar. Enforced + attested.

The user-facing half is one plain-English sheet. Not "requests permission fs.read" — "This add-on wants to: read files you open · send data to the internet." Most modules should legitimately need nothing, and a module asking for nothing should say so loudly. That makes the ones that do ask conspicuous.

The macro problem, which is worth naming

Excel macros run arbitrary code with your full user rights. That design decision is one of the most productive malware vectors in the history of business computing, and it persists because Microsoft can't remove it without breaking thirty years of workbooks.

We have no such debt. A script here is a sequence of registry commands running under the document's capability set. A macro that wants to reach the internet has to ask, in plain English, and can be refused while everything else still works. That's not us being careful — that's a materially better product for anyone who has ever been afraid to enable content on a spreadsheet a stranger sent them.

07 — WHAT WE WRITE

Never inherit a model. Freely use a mechanism.

This section was wrong in v2 and you caught it from the premise alone. Here is the corrected rule, and what it costs.

The error

v2 said: "We do not write a font shaper, a zip parser, a PDF writer, or an Excel function library. Those are solved, commodity, and permissively licensed."

Calling something "solved" and "commodity" is the conclusion, stated as if it were the premise. It skips exactly the independent evaluation that is supposed to produce our quality. If we adopt someone's library, our starting point is wherever their analysis stopped — and we inherit every judgement they made without ever making it ourselves.

And it produced a concrete, checkable contradiction. See below.

The rule that replaces it

The question is not "build or use." It is what kind of thing is this?

KindDefinitionRule
Model An opinion about what the thing is. A workbook class. A cell's semantics. A document representation. Someone decided what matters and what to discard. ALWAYS BUILD. Adopting one makes our architecture downstream of their analysis — permanently and invisibly.
Mechanism A transformation with a provably correct answer and no opinion. DEFLATE. SHA-256. Glyph shaping against the OpenType spec. USE FREELY. There is no "our take on inflate." Rewriting it produces a worse answer, not a more purposeful one.

This is a sharper rule than either "build everything" or "stand on shoulders," and it makes the instinct operational instead of a mood. Applied honestly, it moves four things.

The contradiction your pushback exposed

v2 chose ExcelJS to read and write .xlsx. ExcelJS has its own workbook model and silently drops what it does not understand — charts, conditional formatting nuances, pivot definitions.

v2 also set the Stage 1 gate at "25 real files round-trip with zero differences."

ExcelJS structurally cannot pass that gate. I set a quality bar and simultaneously chose a dependency that makes it unreachable — and the two sat four sections apart in the same document. You found it without seeing a line of code.

What falls out — and it's a better product, not just a purer one

Parsing OOXML ourselves against the published ECMA-376 spec unlocks a technique no wrapper library can offer, because every wrapper's job is to throw away what it doesn't model:

Parse what we model. Keep everything else as opaque XML. Write it back byte-for-byte.

Preserve-unknown. Open a workbook with a pivot table we don't support: we model the cells, retain the pivot XML untouched, and write it back exactly. The user's file survives us intact even where our features stop.

That is the single biggest reason people don't leave Excel — "I opened it in the free one and it wrecked my file." Everyone loses this, because everyone routes through a lossy intermediate model. It's a moat, and it exists only because we refused the shortcut.

The one place I'm deliberately not applying the rule at full strength

CRDTs — the maths behind conflict-free collaborative editing. Yjs's document model is a model and we won't adopt it. But the convergence algorithm is a mechanism with vicious adversarial edge cases, and a hand-rolled version is more likely to lose your data, not less. Silent data loss is the one failure that ends a free spreadsheet's reputation permanently.

So: use the algorithm, never the document representation. And since collaboration isn't in Stage 1 or Stage 2 anyway, the decision is deferred until it's actually in front of us — with real code to judge it against instead of a principle.

What it costs — the honest number

Stage 1 goes from ~10–14 weeks to ~18–24. That's close to a doubling, and it's the direct price of your principle. It's the right call, but you should see the trade you're making rather than have me quietly absorb it:

  • The Stage 1 gate becomes reachable — it wasn't, with a lossy dependency.
  • Lossless round-trip becomes a genuine moat rather than a claim.
  • The Formualizer risk (v0.7.1, one maintainer) disappears entirely — it's no longer in the stack.
  • No dependency can abandon us, churn its API, or relicense underneath us.

The dependency rule, enforced by the build

For the mechanisms we do use: permissive only — MIT, Apache-2.0, BSD, ISC, MPL-2.0, CC0. No GPL, no AGPL, no dual-licensed-with-a-commercial-escape-hatch — that last is the trap, because it looks free until you read the terms. It's why HyperFormula (GPLv3-or-paid) was rejected. CI scans the tree every commit and fails the build on violation.

08 — THE QUALITY PROBLEM

Free software loses on taste, not features

You said free software becomes worthless the moment it drops below the paid version. Agreed — and I want to be precise about where free software actually loses, because it's not where people assume.

LibreOffice has more features than most people use, opens nearly every file, costs nothing, and has existed for fifteen years. It has not won. Not because of a missing feature — because using it feels like using software from 2009. It loses on taste.

The counterexample is the one that matters: Blender. For years it was "the free one" that professionals politely avoided. Then version 2.8 shipped a ground-up interface redesign — and Blender became the tool studios choose over software costing thousands per seat. Nothing about the license changed. The rendering engine wasn't the unlock. Design was.

The moat is not the code. It's that the whole thing feels like one considered object rather than a hundred contributed pieces.

So: one design system, one interaction language, one typographic voice, across every app, from the first commit. Not applied at the end. Every app inherits it by construction — the same way every app inherits the node graph.

Where "the free one" is allowed to be better, not merely equal

Parity is a losing frame. These are places where a clean start beats thirty years of compatibility debt, and they're what Sheet should be known for:

  • "Why is this number wrong?" — click any cell, see the full chain of what produced it. Excel's audit tools are an afterthought; ours is the point.
  • Real version history — every edit, forever, local, free. Not a cloud subscription feature.
  • No silent data destruction — Excel still converts gene names to dates and still models 1900 as a leap year for compatibility with a 1980s bug. We import faithfully and never mangle.
  • Instant open — no splash screen, no account, no sign-in wall, no "loading your workspace."
  • Real numbers — correct decimal arithmetic for money. 0.1 + 0.2 is a genuine and famous source of financial spreadsheet error.

10 — YOUR OTHER MODELS

Where Codex earns its subscription

Specific jobs where a second model is genuinely better than me checking my own work — not a vague "get feedback."

  1. Differential formula testing. Codex generates thousands of adversarial workbooks — edge cases, date boundaries, error propagation, circular references. We run each through our engine and through headless LibreOffice as an independent oracle, and diff. This catches the failure mode that matters most: a formula engine that looks right and is quietly wrong in the 400th case. Fully automatable and it runs forever.
  2. Red-teaming the capability broker. Hand Codex the manifest spec and the broker source with one instruction: escape it. Adversarial by construction, which is the only way a security boundary gets tested honestly. Anything it finds becomes a permanent test.
  3. Design critique before every ship. A second model reviewing screenshots against a written rubric catches what I'm blind to — I've been staring at it, so I can't see it. This has repeatedly been the difference on your past deliverables.
  4. Round-trip fuzzing. Generate .xlsx, import, export, re-import, diff. Any drift is a bug that would otherwise reach a user as silent data loss — the single worst thing a free spreadsheet can do to its own reputation.

If you want a third opinion in the loop, one more frontier model is worth it specifically for #2 and #3 — security and taste are where independent judgement pays. Not needed for the rest.

11 — RISK

What actually kills this

Highest It dies of ambition

By far the most likely outcome. Six half-apps, none good enough to use, enthusiasm gone. This is how nearly every project of this shape ends.

Mitigation: One app at a time, binary gates, and Stage 2 cannot begin until Stage 1's gate is green. The gate is the whole defence — the moment it becomes a judgement call, this risk is live again.

High Quality plateaus at "good, but not Excel"

The exact failure you named. Free software that's 80% as good is worth roughly zero, because switching costs more than the licence.

Mitigation: The 25-file round-trip test and ten real users are pass/fail, and the "better than Excel" list in §8 means we're not competing on parity — we're competing where a clean start actually wins.

Medium Formualizer stalls or churns

v0.7.1, ~1,266 downloads, one maintainer, 22 releases in six months. Any of: abandonment, breaking API churn, or a wrong answer we inherit.

Mitigation: Already priced in — swappable interface, two named fallbacks, and the dependency graph is ours regardless. This risk is capped at "swap a library," not "restart."

Medium Nobody comes

Excellent software nobody finds. Distribution is the part engineers reliably underestimate.

Mitigation: Stage 4 is a real workstream, not an afterthought. And the wedge is a verifiable fact, not marketing: the leading modern open-source suite paywalls opening a file and printing. "Nothing here is ever gated" is a claim we can prove and they cannot match without changing their business model.

Medium One person is the whole project

Bus factor of one, whether that's you or me.

Mitigation: Permissive licence, public repository, documented architecture from commit one. The project survives its author by construction — which is also the honest argument for D1.

Checked and not a risk

File format legality — .xlsx and .pptx are OOXML, published as ECMA-376 and ISO/IEC 29500, openly specified and implementable. LibreOffice has done it for fifteen years. Cost of running it — static downloads on Cloudflare, peer-to-peer sync, no accounts and therefore no database and no breach liability. Effectively $0/month. Windows install friction — SignPath Foundation signs qualifying open-source projects free, which clears SmartScreen; Azure Artifact Signing at $9.99/mo is the fallback.

What this plan deliberately does not do

  • No Word replacement in year one. Rich text layout is a deceptively enormous problem, and Doc is the least differentiated of the three — everyone already has a free writing tool they tolerate.
  • No cloud, no accounts, no server. Not to save money — because accounts create lock-in, liability, and a business model we don't want. Collaboration is peer-to-peer.
  • No mobile apps in year one. The web version works on a phone. Native mobile is a separate discipline.
  • No feature parity claim, ever. We compete on the 95% plus the things a clean start makes possible — not on a checklist against a thirty-year product.
